# M26 — Gateway restart fail-open

The gateway container is created with a Docker restart policy
(`--restart unless-stopped`, `sandboxd/sandbox-core/src/gateway.rs:656`–`:657`
and the shared argv builder at
`sandboxd/sandbox-docker-argv/src/container.rs:524`–`:525`) so a crashed
gateway process comes back without operator intervention. When Docker —
rather than the daemon — does the restarting, the replacement container
starts in a brand-new network namespace, and nothing re-injects the `inet
sandbox` nftables ruleset into it or even notices the gap: the daemon's
health predicate reads five-process liveness only (Envoy, mitmdump,
CoreDNS, the two nft-loggers) and reports `Healthy` for a gateway with no
ruleset at all. The enforcement floor a session's egress policy depends on
can silently vanish while the session keeps running and keeps reporting
healthy.

**What escapes, since the title names the failure and not the damage.**
§19.6 of the trace walks the ruleset for the degraded state, and the answer
is narrower and sharper than "enforcement is off". `inet sandbox` holds the
tree's only `hook forward` chain, so with it absent *"no chain exists at
the forward hook at all"* — not a chain with a weaker policy. The nat
chains of `sandbox_dnat` do come back (see the two degraded states below)
and they still contain TCP — every flow DNAT'd to Envoy or to the
deny-logger — and UDP — allowed flows accepted, everything else logged and
dropped. What leaves is **IPv4 non-TCP/UDP**: ICMP, and as a `[inferred]`
candidate set SCTP, DCCP and UDP-Lite — §19.8's own closed list, and the
reason it stops there must not be dropped when the sentence is restated.
§19.6's ruleset walk does say "and every other IPv4 protocol number", but
that is the *ruleset's* coverage gap; §19.8 then narrows what the
**workload** can push through it, measuring the lite argv as `--cap-drop
ALL` with no `CAP_NET_RAW` — *"so no raw sockets, and GRE/ESP/AH are out of
reach."* A phrasing that ends "and every other protocol number" silently
re-admits those three. Such a packet matches no `sandbox_dnat` rule
except the metadata-address drop,
falls off the end of a nat chain whose default policy is `accept`, reaches
a forward hook with no chain on it, and is then *"masqueraded on the way
out"* by the bare unguarded `masquerade` in postrouting. §19.7 halves the
surface and does it outside nftables: the IPv6 leg is shut by
`--sysctl net.ipv6.conf.all.forwarding=0`
(`sandboxd/sandbox-core/src/gateway.rs:654`–`:655` — the `"--sysctl"` argv
element and its value string), so the hole is IPv4-only.
§19.8 measured that the lite workload can create an ICMP socket and
transmit under its exact hardening flags, which is what makes the escaping
set non-empty; it establishes nothing about reachability of any particular
destination, and its own negative control failed. §19.9 ranks the result,
and the ranking carries a comparison class that a shorter quotation's
ellipsis swallows: *"This is fail-**open** and silent: no probe reports it
(§15.3), the container is `Healthy` throughout (§4), two of the three
tables are present (§4), and the escaping traffic is masqueraded so it does
not even look anomalous at the egress. **Option B and the §18 rig are
fail-closed both ways.** This should be fixed first."* "Fixed first" is
relative to those two named work items, which the trace grades fail-closed.
It is not an absolute priority ranking over the project's queue, and the
quotation marks must not be allowed to lend the trace's authority to one.

**Evidence status: one measured link, one source-derived analysis.** Both
come from the trace at
[`../../../.tasks/handoffs/20260821-0130-policy-delivery-denominator-trace.md`](../../../.tasks/handoffs/20260821-0130-policy-delivery-denominator-trace.md),
and they are not the same kind of claim.

**Measured (§10):** that a restarted gateway container comes back without
the nftables rules the daemon installed. A rig run on 2026-08-21 exercised
three triggers — `docker restart`, `docker stop`+`start`, and PID 1 exiting
under `--restart unless-stopped`, which is the production shape — and an
`inet`-family marker table went PRESENT → ABSENT in all four observations,
each arm asserting the marker present beforehand so that a table which
never loaded could not read as a clean discard. §10.1's population
qualifiers are narrow and are the trace's own: this host's colima Docker,
the real `sandbox-gateway:0.1.11` image, entrypoint overridden to a sleep
loop so the five-process pipeline did not run. The production lite path
runs Docker *inside the gateway Lima VM* — a different daemon on a
different kernel — and §10.1 labels the transfer to it `[inferred]`;
nothing here upgrades that. §10.4 carries into M26-S1's choice of
verification instrument: the netns inode was *identical* across every arm
and would have supported "namespace reused, rules should persist," the
opposite of the measured result. What showed the sandbox had been rebuilt
was eth0's MAC and Docker's embedded-resolver source ports. A plausible
indicator can be structurally blind to the change it was picked to detect,
which is why M26-S1 below requires its instrument to be demonstrated
against that change rather than merely named.

**Source-derived (§15, §17, §19, §21–§23):** which code paths do and do not
react to that link — the barriers below, the health predicate, the recovery
arms, and the ruleset walk above. That is a control-flow read of source at
a pinned commit (`2bf2d14`), not a reproduction. The Linux analysis in
particular (§23) is a derivation from code that is textually identical on
both targets (`sandboxd/sandbox-core/src/gateway.rs` and
`sandboxd/sandbox-docker-argv/src/container.rs` both carry zero `target_os`
occurrences), not a second, independent observation — worth holding onto
because it is easy to over-read "the mechanism holds on Linux too" as "we
saw it happen on Linux," and nothing in §21–§23 supports the stronger
claim. §23.8 states it from the trace's own side: the runtime observation
was on macOS.

§21.9 names three independent barriers, any one of which alone keeps the
hole open: **(1)** the daemon has no signal that the enforcement floor is
gone. §21.8 enumerates every way the daemon can currently *ask*, in three
bullets, and M26 reproduces the enumeration rather than substituting for
it: `docker events` / `DockerOp::Events` — **zero matches** anywhere in the
tree; `RestartCount`, `StartedAt`, `FinishedAt` — **zero matches**, which
matters below because M26-S1 records `{{.State.StartedAt}}` as the route
not taken, and this is the measurement showing that route would have had to
be built from nothing rather than reached for; and container `docker
inspect`, whose `InspectFormat`
(`sandboxd/sandbox-docker-argv/src/container.rs:356`–`:377`) is a closed
six-variant enum of which §21.8 concludes *"None carries a restart count or
a start time."* That is the source's claim and M26 keeps it at that
strength — **not** "none reads incarnation identity", which is false:
`InspectFormat::StatePid` reads `{{.State.Pid}}`, which *is*
per-incarnation, and M26-S1 rejects it on reliability rather than
expressibility grounds. To §21.8's three bullets M26 adds one observation
of its own, which is not in that section and is not carried by its
authority: `NftTable`
(`sandboxd/sandbox-docker-argv/src/gateway.rs:304`–`:307`) names only the
two tables the policy plane manages, not the floor. §21.8 states its own
scope and M26 keeps it rather than restating the measurement as a
universal: *"this enumerates every way the daemon can currently ask — it
does not prove no other mechanism could observe a restart. It proves the
two obvious ones are absent and the typed seam does not offer a third."*
One such mechanism does exist on the current wire, and M26 rejects it on
grounds that are not inexpressibility — see M26-S1's rationale.
**(2)** the health predicate that would act on that observation answers a
liveness question instead of an enforcement one — and it is asked twice
from a single source.
`gateway_status` runs `/healthcheck.sh` from outside, and Docker's own
`HEALTHCHECK` runs the same script and caches the verdict the monitor
consults *first*; §21.3 is explicit that the two passes "are not
independent evidence; they are one measurement read twice," and both answer
`Healthy` for a rule-less container. `gateway_status`'s own doc-comment
states the invariant it depends on ("the nftables deny-all floor is in
place from t0") as a reassurance rather than a failure condition, true of a
container `create_gateway` built and false of one Docker restarted;
**(3)** on macOS, the recovery arm the predicate would route into matches
`BackendKind::Container`, logs, and `continue`s (§21.4) — a correct
decision on its own terms, since it re-creates a macvlan-parented
full-backend gateway lite sessions have no slot for — but it has no
lite-shaped alternative beside it. §23 shows barrier 3 does not exist on
Linux: the recovery arm there is
`#[cfg(not(target_os = "macos"))]` with no backend filter at all, so on
Linux the hole is held open by barrier 2 alone, and clearing it routes
control into an arm that already repairs everything. §23.4 states the
asymmetry the identical predicate-level fix produces — self-healing on
Linux, a monitor that detects, logs, and `continue`s past the failure
every 30 seconds forever on macOS — and asks only that it be carried
forward: *"anyone implementing this needs that asymmetry stated up front,
because a fix validated on Linux would look complete and would change
nothing observable on macOS lite."* **M26's response to that asymmetry is
to fix barriers 2 and 3 in one session** (M26-S2), because a session that
cleared barrier 2 alone would look complete while repairing nothing on the
platform that needs it. The grouping is this milestone's decision; §23.4
proposes no remedy.

**A second trigger reaches the same end state, and on that one the daemon
is the cause rather than a bystander.** Everything above describes Docker
restarting one gateway container. §17.4 records the other route, and rates
it *"more serious, because here the daemon is the cause rather than a
bystander"*: `recover_gateway_lima` restarts the **whole gateway Lima
instance**, having first snapshotted the sessions it will re-create via
`sessions_to_recover` — Running **Lima** sessions only. Lite sessions are
not in that snapshot: not tagged `Degraded`, not re-created, not tagged
`Error`, `networking_status` untouched throughout. Their gateway containers
come back under Docker's restart policy, rule-less, and the recovery loop
that just ran excluded them. §17.4's verdict on the filter is the half a
sweep most needs, because it is the opposite of the half §21.12 attaches to
the same site: *"The `sessions_to_recover` filter is not obviously wrong on
its own terms — it selects what the Lima per-session re-create can rebuild.
As with 17.1, **the defect is not in the filter but in the absence of
anything on the other side of it.**"* Both readings of that site are
correct and neither displaces the other — §21.12's, that the exclusion is
genuinely construction-enforced and a sweep must not flag it; §17.4's, that
nothing stands on the other side of it. M26's repair, placed where M26-S2
places it, **likely** covers this population as a consequence — §17.4 says
that with the §15 probe those sessions *"would report `Unhealthy` and hit
`:12940`"* (that is `sandboxd/sandboxd/src/main.rs:12940`, the macOS
`BackendKind::Container` skip site) — but no criterion anywhere in this
milestone restarts a gateway
Lima VM, and §23.6 records that the Lima-instance recovery path never runs
in a Linux daemon, so no Linux tier can reach the trigger either. That
coverage is therefore inferred at M26's start and still inferred at its
end. Two specific things stay untraced and are filed rather than claimed
(see M26-S3's deferral list): whether the monitor's macOS-only
recovering-latch skip (`sandboxd/sandboxd/src/main.rs:12736`) suppresses
the monitor for those sessions during or after `recover_gateway_lima`, and
whether a repair that re-creates N lite gateway containers inside a
just-restarted VM, once per monitor cycle, behaves.

### The lifetime constraint, the probe target, and what M26 leaves standing

Everything in this subsection binds every session below. Each session's own
block restates the part it has to obey; this is where the reasoning lives.

**The constraint, and its two scopes.** The trace declines to propose a
remedy, and says why twice, at two different scopes. Both are true and
neither reduces to the other.

*Narrow.* §21's scope note: *"No remedy is proposed here, per the standing
ruling that the permit/deny lifetime asymmetry (§17) **may disqualify the
obvious patch.**"* "The obvious patch" is defined there, not left open —
§21.9 names it: *"make the healthcheck read nftables" — clears barrier 2
and leaves 1 and 3 untouched, producing a monitor that correctly detects
the failure, logs a warning, and then `continue`s past it every 30
seconds.* M26 is not that patch; it clears all three barriers. On this
scope alone, the named disqualification target does not reach it.

*Broad.* §21.11, quoted in full because the half that constrains is the
half a summary drops: *"§21.9 names three barriers because the count is the
finding; it is not a work plan, **and the lifetime asymmetry in §17 still
governs what an acceptable fix may look like.**"* Unqualified — it governs
*an acceptable fix*, not one class of fix.

Reading only the narrow scope discharges the question ("M26 clears all
three barriers, so it is unaffected"). Reading only the broad one forbids
M26's approach outright, which the trace does not support and §19.9
contradicts in as many words: *"§4's recovery design does not change.
`setup_macos_lite_gateway` alone reinstalls `inet sandbox` via
`inject_deny_all`, which is W1, which is the only thing that can restore a
forward chain. The census confirms the §17.2 decision rather than reopening
it."* Detect-and-repair is not forbidden. Both scopes are carried here
because neither on its own is the constraint.

**Where the rule is actually stated — §22.3a, not §17.** §17.3 carries the
*evidence*: the policy plane's re-render *"never emits `table inet
sandbox`"*, and the deny-all base is installed at exactly three non-test
sites, all of them create paths. The rule itself is ruled in §22.3a: *"A
permit and its corresponding deny must not live in tables with different
lifetimes"* is precisely *"do not let this rule's correctness depend on
another table's recovery schedule."* The instance it governs is this
milestone's subject — §22.3's table row 1: the bare `masquerade` sits in
`sandbox_dnat`, which self-heals at every DNAT injection; the `reject` that
would stop what it forwards sits in `inet sandbox`, which never self-heals.
Anyone checking the constraint by opening §17 will find no "must not" there
and may conclude the citation is loose or the constraint soft. It is
neither: read §22.3a for the rule and §17.3 for the evidence.

**M26's ruling: the asymmetry is accepted as residual, not removed.** Ruled
by the milestone owner on 2026-08-21. This is M26's own decision, not
something the trace licenses or requires — the trace proposes no remedy and
explicitly declines to. Removing the asymmetry structurally would mean
making the deny share the permit's lifetime, e.g. emitting `inet sandbox`
from the per-policy render path (`render_two_table_ruleset`,
`sandboxd/sandbox-core/src/policy.rs:735`), and that is a different change
of a different size with at least one untraced interaction: `TEARDOWN_RULESET`
(`sandboxd/sandbox-core/src/gateway.rs:1555`–`:1558`) deletes only
`sandbox_dnat` and `sandbox_policy`, so a three-table render would put
`inet sandbox` on the render path while teardown still excludes it. Nobody
has traced what that does. The ruling closes the option for this milestone;
it is not a finding that the option is hard or unavailable.

**What the ruling leaves standing, written as what breaks.** After M26 the
permit and its deny still live in tables with different lifetimes. The bare
`masquerade` comes back on the first allowed DNS query; the `reject` comes
back only when the gateway monitor next runs, observes the floor's absence,
and repairs it. So a Docker-initiated gateway restart still opens a window
in which IPv4 non-TCP/UDP traffic from the workload is forwarded and
source-NAT'd out of the gateway's own address while the session reports
healthy. M26 shortens that window. It does not close it and it does not
make the two lifetimes the same. §22.3a's *"Instance 1 remains the open
one"* is **not** discharged by this milestone, and a later reader must not
infer closure from M26 completing.

**How long that window is was overstated here, and the overstatement was
the milestone owner's.** An earlier draft of this section — and the M26
block in [`../session-plan.md`](../session-plan.md) — recorded the residual
as *"bounded at one gateway-monitor cycle rather than unbounded"*. The
source does not carry that bound, and two measured facts push it out.
§15.5's scoping notes record that `DockerHealth::Starting` **also**
`continue`s (`sandboxd/sandboxd/src/main.rs:12811`–`:12816`), so nothing
acts on a failing check inside the start period; and the gateway
image's own `HEALTHCHECK` sets `--start-period=30s`
(`networking/gateway/Dockerfile:173`), so after a restart Docker reports
`starting` until its first successful probe. §17.4 supports only *"the 30 s
monitor sees them"* and states no bound at all. **What the source supports
is this: the window closes at the first monitor tick that both reaches the
enforcement predicate and acts on it — which is at least one monitor cycle
and, on the periodic path, not before Docker's start period has elapsed and
the cached-health short-circuit has stopped answering `Starting`.** Whether
M26-S2's resolution of that short-circuit shortens it further is that
session's to determine and record. No clause below grades the residual
"within one cycle" by eye, and the macOS replay below records the measured
delay instead.

**Where this residual is durably written down is undecided, and the
undecidedness is itself an instance of the class.** §22.3 rules that this
class's remedy is not vigilance: *"the dependency has to be written at the
site, in the artifact, where a local reader is standing. That is what makes
§22.2 a ruling about a comment rather than a note in a handoff — **a note
here is exactly the non-local form that fails.**"* The only artifacts
carrying the residual today are this milestone document, its block in
[`../session-plan.md`](../session-plan.md), and a progress log. All three
are the non-local form, and this one is not tracked by git. §22.3a's
operative consequence is that instance 1 *"[has] remedies of the same shape
waiting to be derived"* — §22.2's shape being a comment at the site,
written per §22.5 as a failure condition: what breaks when the two tables'
lifetimes diverge, and that M26 bounded the divergence rather than removing
it. The candidate sites are the bare `masquerade` in `sandbox_dnat`'s
postrouting and the `reject` in `inet sandbox`. **This document is not that
remedy and does not stand in for it, and no session below commissions one.**
The durable home is undecided; it is filed as follow-up work in M26-S3's
deferral list, and a reader who finds only this paragraph has found the
form the source names as failing, not the fix.

**The probe target is a correctness requirement, not a wire-shape cost.**
Any enforcement read this milestone ships asserts on `inet sandbox`, by
exact name, on its presence. Three requirements, three distinct failure
modes:

- **On `inet sandbox`, never on `sandbox_dnat` or `sandbox_policy`.** §17.3
  consequence 3: *"`inet sandbox` is the only table nothing reinstalls, so
  it is the only table whose absence is a durable signal. Asserting on
  `sandbox_dnat` would additionally be flaky in the fail-open direction —
  it self-heals on the first DNS query."* The self-heal is
  `generate_domain_ip_rules` → `inject_nftables_ruleset_public`, running
  from the DNS-propagation pass
  (`sandboxd/sandbox-core/src/dns_propagation.rs:527`), from policy apply,
  and from the synchronous DNS gate **once per allowed DNS query** — §17.3
  for the *allowed* qualifier, which is what makes this the D1 → D2 trigger
  and is the trace's own statement of the self-heal condition;
  `GateService`'s doc-comment
  (`sandboxd/sandbox-core/src/dns_gate.rs:192`–`:194`) says "per-request"
  and supports the frequency but not that qualifier. It emits
  `render_two_table_ruleset` — full table definitions with `flush table`,
  so `nft -f` recreates an absent table — and *"It never emits `table inet
  sandbox`."* A probe on either policy-plane table therefore reports green
  in exactly the broken state. This is the reason M26-S1's wire addition is
  the one it is, and not a lower-cost variant.
- **Exact-name lookup, never a substring match.** §15.4: `sandbox` is a
  proper prefix of `sandbox_dnat` and `sandbox_policy`, so
  `nft list ruleset | grep -q 'table inet sandbox'` *"passes on a container
  that has DNAT but no deny-all — i.e. it reports healthy in exactly the
  case this check exists to catch."* §15.4 also requires the reason travel
  with the line, not with the prose: *"Without the reason at the site, the
  next person writes the grep back, and the regression is silent because
  both forms exit 0 on a healthy container."*
- **Presence, not contents.** §15.4: *"'Deny-all base' names what creates
  the table, not what is in it in steady state"* —
  `generate_input_allow_ruleset` and `generate_forward_allow_ruleset` flush
  and replace both of its filtering chains at DNAT time. A probe expecting
  a `policy drop` deny-all input chain is wrong in steady state. §17.3a is
  the trace's own record of reasoning from the table's name to its contents
  and producing a false finding.

**§22.5's probe corollary is the test every predicate this milestone ships
has to pass.** §22.5's comment rule — write the dependency as a failure
condition, not as a reason things are fine — has a form about *mechanisms*
rather than comments, and M26 acts on its content in several places without
having stated it: *"asked about a rule-less gateway the health check
answers `Healthy`, and **its presence is what forecloses the question.** A
gateway with no health check at all would have been safer, because someone
would have gone and looked."* A probe that answers the wrong question is
worse than no probe, because it consumes the impulse to check. So the
question to ask of any predicate below is not "does it answer" but "when it
answers `Healthy`, what has it foreclosed?" Two consequences that bind:
a read the daemon cannot complete is not `Healthy`; and a read that is
short-circuited before it runs is not a probe at all — which is why
M26-S2's cached-health design call is a correctness question and not a
tidiness one, and this corollary is the criterion that call is graded
against.

**Scoped out by ruling, and stated here because M26's chosen route makes it
true: Docker's own health verdict keeps saying `healthy` for a rule-less
gateway.** The read this milestone ships is a Rust/broker-side one, and
M26-S1's rationale argues that route against a `healthcheck.sh`-side `nft`
invocation. The milestone owner ruled on 2026-08-21 that M26 does **not**
rewrite `/healthcheck.sh`'s logic: it is a different build-and-ship path,
through the gateway image, and widening a milestone to reach it is how
milestones sprawl. The consequence, which no bullet in any session below
removes: after all three sessions,
`docker inspect --format '{{.State.Health.Status}}'` still returns
`healthy` for a gateway with no enforcement floor, on both platforms,
unchanged from today — the container's own `HEALTHCHECK`
(`networking/gateway/Dockerfile:173`–`:174`) keeps running the same
liveness-only script and keeps that verdict live in Docker. What changes is
that the *daemon's* enforcement decision no longer rests on it (M26-S2's
scope is where that is made non-optional). What does not change is what an
operator, an orchestrator, or any future code path reading container health
sees. So `/healthcheck.sh` remains, in §22.5's exact terms, a check *whose
presence forecloses the question* — and it is the **stronger** instance of
the class M26-S3 is retiring the weaker instance of (`gateway_status`'s
doc-comment). Applying §22.5's rule to the weaker instance and skipping the
stronger one is not defensible, so M26-S3 does two things about it and no
more: it writes the dependency at the script's own site as a failure
condition, and it files the script's verdict itself as follow-up work. The
script is out of scope by ruling, not by oversight.

**Two degraded states, and an instrument that can convert one into the
other.** §17.3 consequence 1: *"The observable damage shrinks on its own. A
rule-less gateway that then serves one allowed DNS query gets
`sandbox_dnat` and `sandbox_policy` back. Anyone who inspects the ruleset
after the session has done any network activity sees two of three tables
present and may conclude the restart was harmless."*

- **D1 — immediately after the restart, before any allowed DNS query.** No
  sandbox tables at all. A TCP egress probe is **not** blocked.
- **D2 — after the first allowed DNS query.** `sandbox_dnat` and
  `sandbox_policy` are back; `inet sandbox` is not. TCP and UDP are
  contained per §19.6, so a TCP egress probe **is** blocked with the
  enforcement floor still absent. This is the state §17.3 says an observer
  normally finds.

**Both rows carry the same label, because both rest on the same evidence:**
`[measured/enumerated]`, which is §19.9's own grade for §19.6's walk — an
enumeration of source and gates plus an emission test, not an observation
of traffic. §19.10 states the gap once, and without qualifying which
degraded state it means: *"Everything above is a ruleset + gate enumeration
plus an emission test; **no packet has been observed leaving a real gateway
in the degraded state.** That repro is the one thing that would move this
from enumerated to demonstrated, and it needs a real lite session plus an
induced container restart."* Neither row is better evidenced than the
other. Labelling D1 `[inferred]` against a `[measured]` D2 would assert a
comparison the trace denies, and would read as though a packet had been
observed escaping in D2; none has, in either state. M26-S2's macOS replay
carries a non-gating clause to attempt that observation once while the rig
is standing.

Two consequences bind every criterion and every test below. First,
**TCP/UDP egress reachability is not an enforcement observable, and no
clause below may rest on it.** In D2 a TCP or UDP probe reports "blocked"
both before and after a repair, so a criterion resting on it cannot fail
for the reason it exists; and re-blocked TCP/UDP egress is consistent with
`inject_deny_all` never having run at all, because `sandbox_dnat`'s
prerouting DNAT is what contains those flows and the policy plane restores
it unaided. The ground for that is §19.6's walk of the two nat chains —
not the observation that a blocked probe looks like evidence of a repair,
which is the reading it displaces. Second, **an egress probe issued by
hostname resolves first**, and an allowed lookup is itself the D1 → D2
trigger, so such an instrument converts the state before measuring it.
`[inferred]`, not traced end to end, and flagged rather than asserted.

So: every criterion and every test below whose purpose is to evidence
enforcement either asserts on `inet sandbox`'s presence by exact name, or
probes a protocol §19.6 places outside `sandbox_dnat`'s coverage (IPv4
non-TCP/UDP; ICMP is the one member §19.8 measured as emittable) — and
names which degraded state, D1 or D2, it observes.

The repository's integration tier is Linux-only by construction (`make
test-integration`'s prerequisites call `setcap`/`getcap`, which have no
macOS equivalent — see `CLAUDE.md`), so the default validation path is
exactly the platform where this fix is invisible: everything passes
whether or not barrier 3 was ever touched. **Every session below requires
macOS lite validation as a named, non-optional exit criterion** — not
folded into a general "tests pass" bullet — because that is the only
platform where a landed fix has an observable effect to check. **M26-S3
additionally requires that the macOS check be automated**, in the e2e
tier — the only tier that can drive a *live* macOS gateway. The unit tier
does run on macOS, and every session below requires it; but the default
nextest profile filters out everything needing out-of-process state
(`CLAUDE.md`'s `integration_*` convention), so it cannot reach a gateway
container at all, and the integration tier cannot run on a macOS host in
the first place. A milestone whose thesis is that manual attention is an
unreliable barrier cannot quietly leave its own macOS half guarded by
manual replay alone. If it turns out that it must, that is a decision for

## M26-S1 — Make the gateway's deny-all floor readable across the broker wire

**Entry criteria.** Fresh.

**Spec reference.** [`../../../.tasks/handoffs/20260821-0130-policy-delivery-denominator-trace.md`](../../../.tasks/handoffs/20260821-0130-policy-delivery-denominator-trace.md) — §15.4 (the exact-name lookup, the substring trap, and the presence-not-contents qualifier), §17.3 (consequences 1 and 3: the policy plane silently restores the wrong subset, and why a probe must assert on `inet sandbox`), §21.1–§21.2 (the repair paths and the single predicate they share), §21.8 (the enumeration of every way the daemon can currently ask, and its own scope note), §21.9 barrier 1 (what the trigger would have to observe), §22.3a (the lifetime rule this read exists to make observable), §23.1's barrier-1 row (that barrier stands identically on Linux, because `sandbox-docker-argv/src/container.rs` carries zero `target_os` occurrences, so the gap and its fix are platform-independent; §23.2 makes the parallel argument for barrier 2, not this one).

**Rationale.** §21.9 presents the three barriers as independent — "any one left standing keeps the hole open" — and §21.11 disclaims the list as a work plan while adding that the §17 lifetime asymmetry still governs what an acceptable fix may look like, so nothing in the trace makes barrier 1 prior to the others. Two properties of the code do. **First, the operand the predicate reads.** The milestone owner ruled on 2026-08-21 that the predicate asks whether the deny-all floor is *present*, not whether the gateway restarted since the last policy injection. Four grounds, and they are M26's: an enforcement-state read needs no stored operand, so it adds no persisted field and raises no on-disk-compatibility question (`CLAUDE.md`); it measures the property the system exists to guarantee rather than a proxy for one cause of losing it; it therefore catches rule loss from *any* cause, not only from a restart; and it fails closed when the container cannot be read. The route not taken is recorded so nobody re-derives it: the restart-generation answer would be `{{.State.StartedAt}}`, freshly drawn per incarnation — not `RestartCount`, which a manual `docker restart` does not increment, and not `{{.State.Pid}}`, whose same-value failure modes (PID recycling; the `0` a stopped container reports, `sandboxd/sandbox-core/src/backend/container.rs:1337`) all land on "miss the restart", which is the fail-open direction. **Second, the read has to cross the broker channel to the macOS operator agent, and the shape it crosses in is not neutral.** The enforcement read has a live home: `ContainerCommand::ListNftTable` (`sandboxd/sandbox-docker-argv/src/container.rs:591`), issued today by the policy distributor's rollback snapshot. Its argv render (`sandboxd/sandbox-docker-argv/src/container.rs:704`–`:710`) is `["nft", "list", "table", "inet", table.name()]` — five argv elements, no shell, with the name supplied by `NftTable::name()` (`sandboxd/sandbox-docker-argv/src/gateway.rs:314`–`:319`), a closed match over string constants. **That is §15.4's required exact-name lookup by construction**: there is no string being assembled, so the substring form §15.4 warns about cannot be written at this seam at all. It is an argument for this route over a `healthcheck.sh`-side `nft` invocation, where the `grep -q` form is one tidy-up away and both forms exit 0 on a healthy container. What the op cannot express is the table this milestone is about: `NftTable` (`sandboxd/sandbox-docker-argv/src/gateway.rs:304`–`:307`) has exactly two variants, and its own doc-comment says what they are for — *"The two `inet` nftables tables the gateway's **policy plane** manages"* — which is precisely why neither serves. The policy plane is what re-renders them, once per allowed DNS query, and never re-renders the floor; a probe built on either existing variant reports green in exactly the broken state (see the framing's probe-target constraint). The addition is therefore not a convenience, it is what makes the read correct. **There is a route that needs no enum addition at all, and M26 rejects it rather than lacking it.** `DockerOp::ContainerExecStdin` with `StdinCommand::ApplyNftRuleset` renders `nft -f -` (`sandboxd/sandbox-docker-argv/src/gateway.rs:365`–`:367`); its validator deliberately does not inspect the body — `validate_stdin_command`'s `ApplyNftRuleset` arm is `Ok(())` (`sandboxd/sandbox-agent/src/validation.rs:1107`), with only a size ceiling applied — and `BrokerResult::Ok` carries `stdout` back (`sandboxd/sandbox-agent/src/protocol.rs:150`–`:157`), so a body of `list table inet sandbox` is a working read channel on today's wire. It is rejected because routing a read through an op whose validator is documented as not looking at the payload converts a reviewed write channel into an unreviewed read channel, and leaves no artifact for a reviewer to see. That is why §21.8's scope note matters and why M26 keeps it: the enumeration covers every way the daemon can currently *ask*, not every way a restart could be observed. M26 does not claim the signal is inexpressible; it claims the honest shape for it is a variant on a closed enum, and landing that variant in its own session is what keeps its cost visible instead of folding it into a predicate change. That cost is stated at `InspectFormat`'s site — variants accreting *"one more variant at a time, each individually reasonable, until the set covers enough of the config that a free string would have been equivalent"* (`sandboxd/sandbox-docker-argv/src/container.rs:342`–`:354`) — and **`NftTable` does not carry that warning**: its doc-comment (`sandboxd/sandbox-docker-argv/src/gateway.rs:297`–`:302`) and its agent-side mirror (`sandboxd/sandbox-agent/src/protocol.rs:808`) are purely descriptive. The obligation is imported from the sibling enum rather than read off this one, which is itself a reason to land it at the site. The addition belongs in `sandbox-docker-argv` because `CLAUDE.md` documents it as the seam both the daemon and the macOS operator agent build `docker` argv from, with the crate carrying zero `target_os` gates: one addition reaches both platforms and neither side can drift from what the other expects. On Linux the daemon drives Docker directly (`DockerRoute::Host`, `sandboxd/sandbox-core/src/docker.rs:469`) so no channel work is needed there, and the enum addition is still required because the argv crate is the shared seam; on macOS the VM route (`DockerRoute::Vm`, `sandboxd/sandbox-core/src/docker.rs:474`) goes through the agent and there is no second path.

**In scope.**

- A `NftTable` variant naming the deny-all floor (`sandboxd/sandbox-docker-argv/src/gateway.rs:304`–`:307`, with its `name()` arm at `:314`–`:319`), rendering the table name exactly as `generate_deny_all_ruleset` emits it — `table inet sandbox` (`sandboxd/sandbox-core/src/gateway.rs:1612`–`:1613`). Closed-enum, pure-function, no I/O, matching the crate's existing shape.
- **The new variant does not join `NftTable::ALL`, and the existing test is the guard.** `ALL` (`sandboxd/sandbox-docker-argv/src/gateway.rs:311`) is documented as *"Both tables, in the order the rollback snapshot reads them"* and is iterated by `read_nftables_state` (`sandboxd/sandbox-core/src/policy_distributor.rs:567`) to build the policy distributor's rollback snapshot. Adding the floor to `ALL` silently widens that snapshot to a table the policy plane does not manage and teardown does not delete. The test `nft_tables_name_the_pair_the_policy_plane_manages` (`sandboxd/sandbox-docker-argv/src/gateway.rs:564`) asserts `ALL.len() == 2`; it fails if the variant is added to `ALL`, and the response is to leave `ALL` alone, not to bump the constant. Related and read before reusing anything: `read_nftables_state` silently omits a missing table (`sandboxd/sandbox-core/src/policy_distributor.rs:584`–`:589`, *"Missing table is fine"*) — correct for a rollback snapshot and exactly wrong for an enforcement predicate, where a missing table is the signal.
- **Both doc-comments become false on the addition and are rewritten in the same change, carrying the reason at the site per §15.4.** `NftTable`'s (`sandboxd/sandbox-docker-argv/src/gateway.rs:297`–`:302`) says *"The two `inet` nftables tables the gateway's policy plane manages"*; `ALL`'s (`:310`) says *"Both tables"*. The rewritten enum comment states the distinction the new variant exists for — the two the policy plane re-renders per allowed DNS query and thereby self-heals, versus the floor nothing reinstalls — and states it as a failure condition rather than a description, per §22.5's rule: what breaks if a caller reaches for the wrong variant, not why the set is fine. It also carries the security-change obligation `InspectFormat` states at its own site and this enum does not.
- Wiring the new variant through both sides of the broker channel, so the invocation the daemon assumes and the one the agent runs cannot drift. Three sites are compiler-forced and one is not. Forced: `NftTable::name()`'s exhaustive match (`sandboxd/sandbox-docker-argv/src/gateway.rs:315`), and the two `From` impls between the agent mirror and the argv crate (`sandboxd/sandbox-agent/src/protocol.rs:1184` and `sandboxd/sandbox-agent/src/protocol.rs:1409`) — both exhaustive, no wildcard arm, neither enum `#[non_exhaustive]`, so a one-sided addition fails to compile rather than drifting silently. The agent-side mirror (`sandboxd/sandbox-agent/src/protocol.rs:811`) is the addition those impls force, which makes the mirror and the two impls a single unit of work.
- **The one site here where drift *is* silent, and it must be opened by hand.** `validate_docker_op`'s `DockerOp::ContainerExec` arm (`sandboxd/sandbox-agent/src/validation.rs:1202`) matches the inner `ContainerCommand` exhaustively, but its no-op or-pattern (`sandboxd/sandbox-agent/src/validation.rs:1220`–`:1224`) reaches this op as `ContainerCommand::ListNftTable { .. }` — a rest pattern over the `table` field, so a new `NftTable` variant is accepted with no compiler complaint. The argv crate states the obligation directly: *"whatever it carries, add the matching agent-side validation in the same change — a field nobody checks is a field the caller controls"* (`sandboxd/sandbox-docker-argv/src/container.rs:568`–`:569`). The disposition may well be "still nothing to validate", since the variant carries no caller-supplied string — but that is a decision to take, and the site already owns the idiom for recording it: `the_policy_plane_reads_carry_nothing_to_reject` (`sandboxd/sandbox-agent/src/validation.rs:3448`) exists, in its own words, *"so the absence of validation is a recorded decision."* Extending that test is what converts absorption into decision.
- The security-change obligation discharged in writing, at the enum's site rather than in a session record. What the caller needs is a durable-absence signal for the one table nothing reinstalls; the check that no existing variant serves it is §17.3 consequence 3's — both existing variants name tables the policy plane self-heals on the first allowed DNS query, so a probe on either is flaky in the fail-open direction. The enum-avoiding route (`ContainerExecStdin` + `ApplyNftRuleset`) is named and rejected in the rationale above so it is not rediscovered as a shortcut later.
- A named, recorded way to read `inet sandbox`'s presence on a running macOS lite gateway — pinned and written down in this session rather than improvised at verification time. Which surface that is — a field on an existing diagnostic, a `sandbox doctor` row, a documented one-off command — is the session's call; that it is pinned, recorded, and **shown to register the change** is not. §10.4 is the warrant: in the rig that measured this failure the netns inode was identical across every arm and would have reported "nothing changed" about a container that had demonstrably been rebuilt. An instrument named but never seen to move is indistinguishable from one blind to what it was chosen for, and an unnamed instrument resolves at execution time to whichever branch is cheapest to claim. The instrument must not be an egress probe and must not resolve a hostname — see the framing's D1/D2 note; the read this session ships resolves nothing and so cannot convert the state it is measuring.
- Unit coverage for the new variant's argv rendering, in the leaf-crate pure-function style the rest of `sandbox-docker-argv` already uses, asserting the exact argv vector including the literal table name rather than that it merely contains it.

## M26-S2 — Make gateway health answer the enforcement question

**Entry criteria.** M26-S1 complete — the deny-all floor's presence is expressible on the broker wire (the third `NftTable` variant, its agent-side mirror, both `From` impls, and the validation arm's recorded disposition) and readable on a running macOS lite gateway through the instrument M26-S1 pinned and demonstrated across the D1/D2 replay. This is a statement of sequencing, not of logical necessity: M26-S1 runs first because a wire shape has to be agreed before anything can consume it, and it deliberately stops short of the health path — wiring the read in is this session's work, not a precondition of it. **No alternative route is left open here.** The milestone owner ruled the enforcement-state route in the framing; this session consumes what M26-S1 delivered and does not re-decide it.

**Spec reference.** [`../../../.tasks/handoffs/20260821-0130-policy-delivery-denominator-trace.md`](../../../.tasks/handoffs/20260821-0130-policy-delivery-denominator-trace.md) — §15.4 (exact-name lookup; presence, not contents), §15.5 (the drafted comment for the skip site, the four-combination matrix behind it, and the ruling to leave the arm's log level at `debug!`; also the `Starting` arm that `continue`s alongside the `Healthy` one), **§17.2 (the standing DECISION: the repair is `setup_macos_lite_gateway` alone, never preceded by `teardown_macos_gateway`; the named implementer trap; the mechanism; and the measurement that this needs no new broker op)**, §17.3 (why the read must target `inet sandbox`, and the two degraded states this session's replays have to distinguish), §17.4 (the second, daemon-caused trigger this session's repair probably but unverifiably covers), §19.6 (what remains contained in D2, and therefore what an egress probe cannot evidence), §19.10 (the end-to-end observation nobody has taken, and the rig this session stands up), §21.3 (the predicate: two liveness steps, then unconditionally `Healthy`; the `t0` doc-comment it depends on; **and** the monitor's earlier read of Docker's cached `HEALTHCHECK` verdict, which runs the same script — "not independent evidence; they are one measurement read twice"), §21.4 (the macOS recovery arm's `BackendKind::Container` match, which logs and `continue`s — correct on its own terms, missing a lite-shaped alternative beside it), §21.6 (why the existing deferral to `restore_session_networking_lite` doesn't reach a running session), §21.9 (the explicit warning: fixing the predicate alone routes into the same discard), §23.1/§23.3 (barrier 3 does not exist on Linux — the recovery arm there is unfiltered and already the right shape), §23.4 (the platform-inverted outcome of this exact fix), §23.8 (`ensure_network` runs in the Linux arm before `restart_gateway`, was never traced, and can fail and `continue`).

**Rationale.** §21.9 and §23.4 supply the facts behind M26's decision to carry both barriers in one session rather than one at a time — the decision is the milestone's, the asymmetry is the trace's. On Linux, `gateway_status` and the unfiltered `#[cfg(not(target_os = "macos"))]` recovery arm are the *same code* that already repairs a `Healthy`-but-empty gateway once it stops reporting `Healthy`, so clearing barrier 2 there is the whole fix. On macOS, the same predicate change with nothing else routes into the monitor's `BackendKind::Container` arm, which logs and `continue`s — a monitor that now correctly detects the failure and does nothing about it, forever, which is a worse-looking state than today's silent gap because it manufactures the appearance of an owned problem. §21.6 rules out reusing the existing `restore_session_networking_lite` path unmodified — its only two callers are explicit, operator-initiated session starts, unreachable from a session that is already `Running`. So this session's macOS half is new code: a lite-shaped repair reachable from the periodic monitor, not a rewiring of what already exists for session-start. Everything this session asserts about enforcement is constrained by the framing's probe-target rule and its D1/D2 note; the constraint is restated at the bullets it binds rather than left to be picked up from the framing.

**In scope.**

The two exits differ in kind: the `Healthy` arm **bypasses** the enforcement question, the `Starting` arm **delays** it. Both must be resolved, and they may want different resolutions; a resolution that reorders past the `Healthy` arm and leaves `Starting` untouched satisfies this bullet's letter while leaving the repair unable to fire during the start period, which is the fail-open direction and is what the framing's restated residual bound is about. **A third arm also never reaches `gateway_status`, and it is named here — out of scope, with the reason — so a later reader does not have to re-derive that it is harmless.** `DockerHealth::Unhealthy` (`sandboxd/sandboxd/src/main.rs:12818`–`:12823`) does not probe at all: it synthesises `GatewayStatus::Unhealthy("docker HEALTHCHECK reports unhealthy")` and falls through to the verdict match at `sandboxd/sandboxd/src/main.rs:12855`, whose `NotRunning | Unhealthy` arm enters recovery. It holds nothing open, and nothing in this session's scope reaches it. "Two exits" above counts the arms that `continue` — accurately; this arm is not one of them, which is exactly why it needs saying rather than leaving as an apparent miscount. **Rationale.** This session closes the milestone on two axes the two implementation sessions could not: proof that the fix actually changes behaviour (M26-S1 and M26-S2's exit criteria are manual replays, not durable regression coverage) and retirement of the specific reasoning that let the gap ship unnoticed for as long as it did. §22.5's ruling is precise about why the doc-comment matters beyond tidiness: the original wording was a *reassurance* ("the floor is in place from t0"), and a stated reassurance is stronger protection for a bug than silence would have been, because it tells a reader not to check rather than inviting them to. §23.7 gives the sweep a concrete second target beyond the `gateway_status` doc-comment already in scope for this session — a comment that was true when written and became silently false for a second platform without ever naming one — and §21.12 is included specifically so the sweep has a verified-true instance to compare against, since §22.3b's retraction record shows how easy it is to report a shape-fitted claim as a finding without reading the site it names. The coverage itself is split by tier because it has to be: the integration tier cannot run on macOS (`CLAUDE.md`), so a single integration-tier test would leave barrier 3 — the only barrier that was macOS-specific — permanently unguarded by anything automated. Closing this milestone with the macOS side resting on manual replay would re-create, inside the fix, the exact structure the fix removes.

**In scope.**

- **Linux regression coverage** — integration-tier (`integration_*` prefix per `CLAUDE.md`'s convention) — that forces a gateway into the enforcement-absent state directly (deleting the `inet sandbox` table without killing the five monitored processes) and asserts the predicate and recovery path react, as distinct from the existing liveness-only coverage that kills a process instead. **What the test asserts is as constrained as how it forces the state**: the assertion is on `inet sandbox`'s presence by exact name, and the test must remain red when the fix is absent *while both policy-plane tables are present* — i.e. it has to cover state D2 (§17.3), not only the moment after deletion. An assertion on TCP or UDP egress reachability is green in both degraded states (§19.6) and does not distinguish a repaired gateway from an unrepaired one; it is not an acceptable assertion here. **D2 is a fixture precondition, not a state the test can assume**: §19.4 records that *"`inet sandbox_policy` legitimately does not exist in some steady states"* — the W2 `policy-flush` and W3 `policy-rollback` writes both `delete table` it — so with an empty or deny-only policy set "both policy-plane tables present" is unreachable by construction and the assertion can never pass. The fixture's session therefore carries a non-empty allow-list with at least one resolvable domain, and **the reason is written into the test**, because the next person to touch the fixture will otherwise read the allowed domain as noise and remove it. The failure this guards against is not a red test; it is the third debugging round, in which the assertion gets weakened to something that passes — which is precisely what this bullet's D2 requirement exists to prevent. This is the test that would have failed before M26-S2 and passes after, and it is what makes "the fix works" a checkable property on Linux rather than a manual claim.
- **macOS regression coverage, automated, in the e2e tier** — because the integration tier above cannot run on a macOS host at all (`CLAUDE.md`), and the unit tier that *does* run there is hermetic and cannot reach a gateway container, so e2e is the only tier that can execute this check on the platform where barrier 3 lived. Without it the macOS half of this milestone is guarded solely by the manual replays M26-S1..S3 require, which is the same shape of protection as the doc-comment this session retires below: a barrier that holds only while someone remembers to check it. That is the failure this milestone exists to close, so reproducing it here is not acceptable as a closing state. The mechanics are the session's to choose — which file, which markers, how a macOS lite gateway is driven into the enforcement-absent state — but two things are fixed: the outcome, that a macOS lite gateway which loses its ruleset is caught by a test and not by a person; and the assertion, which is subject to the same D1/D2 constraint as the Linux test above — including its fixture precondition, that the session carries a non-empty allow-list, since §19.4's `delete table` on an empty policy set makes D2 unreachable otherwise.
